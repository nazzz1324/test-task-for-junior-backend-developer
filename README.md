# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файлы из `migrations/` монтируются в `docker-entrypoint-initdb.d` и применяются только при инициализации пустого data volume. Миграции выполняются в алфавитном порядке: `001_create_tasks.sql` → `002_add_recurrence.sql`.

## API

Базовый префикс API:

```text
/api/v1
```

### Задачи (Tasks)

- `POST   /api/v1/tasks`
- `GET    /api/v1/tasks`
- `GET    /api/v1/tasks/{id}`
- `PUT    /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

### Повторяющиеся задачи (Recurrence)

- `POST   /api/v1/tasks/recurring` — создать серию и сгенерировать первые экземпляры
- `GET    /api/v1/tasks/recurring` — список всех правил повторения
- `GET    /api/v1/tasks/recurring/{id}` — правило по ID
- `PUT    /api/v1/tasks/recurring/{id}` — изменить правило (регенерирует будущие экземпляры)
- `DELETE /api/v1/tasks/recurring/{id}` — удалить серию
- `GET    /api/v1/tasks/recurring/{id}/instances` — все задачи данной серии

## Функция повторяющихся задач

### Типы повторения

| Тип | Поле | Пример |
|-----|------|--------|
| `every_n_days` | `interval_days` (int ≥ 1) | каждые 3 дня |
| `monthly_on_day` | `day_of_month` (1–30) | ежемесячно 15-го числа |
| `specific_dates` | `specific_dates` (массив дат) | только 1 января и 9 мая |
| `even_days` | — | только чётные числа месяца (2, 4, 6…30) |
| `odd_days` | — | только нечётные числа месяца (1, 3, 5…31) |

### Пример запроса

```json
POST /api/v1/tasks/recurring
{
  "task_title": "Ежедневный стендап",
  "task_description": "15 минут в 10:00",
  "type": "every_n_days",
  "interval_days": 1,
  "starts_at": "2024-07-01T00:00:00Z",
  "ends_at": "2024-12-31T00:00:00Z"
}
```

### Логика редактирования и удаления серии

**PUT** — изменяет мутабельные поля правила (`task_title`, `task_description`, `interval_days`, `day_of_month`, `specific_dates`, `ends_at`). Все будущие экземпляры (с завтрашнего дня) удаляются и генерируются заново по обновлённому правилу. Прошлые экземпляры остаются без изменений.

**DELETE** — прошлые экземпляры (до сегодняшней даты) открепляются (`recurrence_id = NULL`) и остаются в таблице `tasks` как обычные задачи. Будущие экземпляры удаляются каскадно вместе с правилом.

### Планировщик

При старте сервиса фоновая горутина (`Scheduler`) сразу генерирует экземпляры на 90 дней вперёд для всех активных правил. Далее она повторяет это каждые 24 часа, поддерживая скользящий горизонт генерации.

## Принятые допущения

1. **Горизонт генерации — 90 дней.** При создании серии экземпляры создаются сразу на 90 дней вперёд (или до `ends_at`, если оно раньше). Планировщик ежедневно продлевает горизонт.

2. **Максимум 365 экземпляров за один вызов генератора.** Защита от непреднамеренного создания тысяч строк при правиле `every_n_days: 1` без `ends_at`.

3. **`type` и `starts_at` иммутабельны после создания.** Изменение типа повторения означает создание новой серии.

4. **`day_of_month` ограничен значениями 1–30.** День 31 намеренно исключён: он отсутствует в 5 из 12 месяцев, что делало бы серию неравномерной. Если нужен «последний день месяца», следует использовать `specific_dates`.

5. **Месяцы без нужного дня пропускаются.** Для `monthly_on_day: 30` февраль всегда пропускается (28 или 29 дней). Для `day=29` — февраль пропускается в невисокосные годы.

6. **`even_days` / `odd_days` — это чётность числа месяца**, а не порядкового номера дня в году. Чётность определяется по `day % 2`.

7. **Задачи без `recurrence_id` работают как раньше.** Обратная совместимость: поля `recurrence_id` и `scheduled_date` в ответах API присутствуют только если не `null` (`omitempty`).

8. **Статус экземпляров по умолчанию `new`.** При создании серии все экземпляры получают статус `new`. Каждый экземпляр — самостоятельная задача, статус которой меняется независимо.

---

## Ограничения

- Нет поддержки изменения типа повторения у существующей серии (нужно создать новую).
- Нет возможности редактировать отдельный экземпляр серии — только всю серию через PUT.
- Миграции применяются только при инициализации пустого Docker volume; для обновления существующей БД нужно применять `0002_add_recurrence.up.sql` вручную.
- Планировщик не персистентен: если сервис не работал несколько суток, при следующем старте он догенерирует пропущенные экземпляры (в пределах горизонта 90 дней от текущей даты).
